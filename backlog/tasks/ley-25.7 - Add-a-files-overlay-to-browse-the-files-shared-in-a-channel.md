## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Once a file message scrolls out of view, finding it again means scrolling the transcript or remembering its hash. The app already indexes every attachment it has seen, so an overlay over that index gives each channel a file browser: a place to save or open files without typing a hash. It follows the `Ctrl+P` jump-to overlay, a modal that stores only its query and highlight.

Clicking an entry could follow if mouse support (LEY-16) is enabled, but the overlay is keyboard-first.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 `/files` opens a modal overlay listing every file shared in the active channel, including loaded and backfilled history, newest first, with name, size, sender, date, and whether it is saved locally
- [x] #2 Typing filters by file name or sender, case-insensitively; Up and Down move the highlight; Esc closes the overlay
- [x] #3 Enter saves the highlighted file the same way `/save` does; a second key opens an already-saved file with the OS default application
- [x] #4 The saved marker survives restarts and shows a file as unsaved again if it was deleted from disk
- [x] #5 The overlay works in group channels, `/msg` DMs, and `/dm` chats, and shows a clear message when nothing has been shared
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Findings (no code needed). The "index" the description speaks of is `AppState::known_attachments` / `Channel::carries_file`: derived on demand from each channel's loaded transcript -- startup history, live messages and backfilled history all end up in `Channel::messages` -- so it is what `/save` resolves against, and it shares its window (`MAX_SCROLLBACK`, 500 lines per channel). The overlay lists exactly what `/save` can fetch. `Ctrl+P` is the pattern: `AppState::switching` holds a `Switcher` (query + clamped highlight), `handle_key` hands it every key, a paste filters it, `is_composing` is false while it is open, and `ui::render_switcher` draws it. "Saved" is different: it is a fact about the disk, which app.rs and ui.rs never touch, and nothing records it today (`NetEvent::FileSaved` only pushes a notice). So AC 4 needs a persisted record of what was saved where, plus a look at the disk done by main.rs.
2. The record of saved files (new `saved_files.rs`, a twin of `dm_registry.rs`: a postcard file `saved_files` in the data directory, rewritten whole on each change, corrupt = empty with a warning, real I/O errors fail startup). One record per (channel stored name, content hash) -> absolute path of the copy. Keyed by channel because every channel has a folder of its own (LEY-25.6): a file saved from #general is not saved in #random, and an overlay for #random should offer to save it there. `record` replaces an earlier record of the same file; `present_in(channel)` returns hash -> path for the records whose file exists now, so a deleted file simply stops counting as saved (AC 4) and counts again if it comes back. Nothing is ever pruned: a drive that happens to be unmounted must not erase what we know. Paths are checked on the way in (absolute, valid UTF-8) so everything downstream can rely on it. Pairing leaves the file alone (facts about this device's disk, like the files root), and so does `/leave` (it never touches a folder either).
3. Telling the record who a save was for. `InputAction::SaveFile` gains `channel` (app.rs already resolves it to pick `dir`); `Net::save_file` takes it, and `NetEvent::FileSaved` carries `channel` and `hash` next to `filename` and `path`, so the event is self-describing and main.rs records on `FileSaved` (a peek, like `DmJoined` -> `dm_registry.record`) with no pending-saves map to leak when a download fails. `run_save` is split: the part that builds the `SaveFile` (providers, folder, the `saving X...` notice) becomes one helper that `/save` and the overlay both use, so Enter really is `/save`.
4. The overlay (app.rs). `AppState::viewing_files: Option<FilesOverlay>`, `FilesOverlay { channel, query, selected, saved }`: like `Switcher` the list itself is never stored -- `files_matches()` re-derives it from the live transcript of the overlay's channel, newest first, one row per share (`SharedFile`: the attachment, sender, timestamp), filtered by a case-insensitive contains on the file name or on the sender as displayed (`display_name`: what is on screen, like the switcher matching labels) -- and `files_highlight()` clamps the position in the one place that reads it. Two things more than the switcher keeps: the channel, fixed when it opens (`activate_or_create_channel` can move focus under an open overlay, and Enter must save into the folder of the channel whose list the user was looking at), and `saved` (hash -> path, what the disk said when it opened). `/files` opens it on the active channel and returns `InputAction::CheckSavedFiles(channel)`: main.rs answers synchronously (`SavedFiles::present_in`, a stat per record of one channel, the kind of fs work `resolve_destination` already does inline) through `apply_saved_files`, before the next draw. A `FileSaved` for the overlay's channel marks the file saved live.
5. Keys. Typing and Backspace edit the query (highlight back to the first match); Up/Down clamp at both ends; Esc closes; Ctrl+C still quits; a paste filters (control characters dropped); other keys, and Ctrl chords, are ignored so nothing leaks into the draft. Enter on an unsaved file closes the overlay and returns the same `SaveFile` a `/save` gives -- progress, success and failure then show in the transcript, which a modal would hide. Enter on a file already saved does nothing, so a file is never saved twice by accident. Ctrl+O on a saved file closes the overlay and returns `InputAction::OpenFile(path)`; on an unsaved one it does nothing. The bottom border says which of the two the highlighted row offers, so neither is a dead key.
6. Opening (files.rs `open_in_default_app`): `open` on macOS, `explorer` on Windows, `xdg-open` elsewhere, the path as its one argument (never through a shell), stdio nulled so the launcher can't draw on the TUI, the child reaped on a thread so it is never a zombie and the loop never waits. main.rs first checks the file is still there and says so if not. No new dependency.
7. UI (ui.rs). `render_files`, drawn over everything like the picker (`overlay_area`, filter row, scroll thumb, highlight style): a gutter with a green check mark for a saved file, the name (cut with an ellipsis before the columns), size, sender, and date -- the picker's day-and-time/day-and-year label (`modified_label` now delegates to a shared `day_label`), applied to the message timestamp. Title `files in #general` with a count (`3 of 12` while filtered); a placeholder says `no files have been shared in this channel yet` or `no matches`. `/files` joins `COMMAND_HINTS`, `/help`, the README, features.md, concept.md.
8. Tests. saved_files.rs: missing/corrupt file, record then present_in, replaced record, channels independent, a deleted file not present and present again once restored, persistence across reloads, a relative or non-UTF-8 path refused. files.rs: the opener is run with the path as its one argument. app.rs: `/files` opens it newest first in group channels, `/msg` DMs and `/dm` chats (the fixture with all three); loaded and backfilled history both listed; own files listed; filter by name and by sender, ignoring case; highlight moves, clamps, resets and survives matches shrinking; Esc, Ctrl+C; keys and pastes never reach the draft; Enter == `/save` (same hash, filename, providers, folder; `channel` set) and closes; Enter on a saved file and Ctrl+O on an unsaved one do nothing; Ctrl+O opens the saved path; `FileSaved` marks live, only for the overlay's channel; the overlay stays on its channel when focus moves; `is_composing`. ui.rs: not drawn until opened; rows with name, size, sender, date; check marks; highlight; filter and cursor; both placeholders; footer per row; covers what is under it; survives a tiny terminal; box centered and never larger than the screen. main.rs: a drop while `/files` is open is a plain paste; pairing leaves `saved_files` alone.
9. Housekeeping: README (`/files` row; the `Esc` row), features.md (new entry), concept.md (File sharing section, project layout line for `saved_files.rs`), `/help` and the hints panel. Cargo.toml 0.4.0 -> 0.5.0 (a feature: minor); Cargo.lock follows the build.
10. Verify with cargo test, cargo clippy --all-targets and cargo fmt --check, then the real binary: two instances under isolated HOMEs, each in a PTY read with pyte (scratch script outside the repo). A shares files in #general; B opens /files (listing, filter, Esc), Enter saves one into the channel folder, reopens to see the check mark, Ctrl+O hands the saved path to a stand-in `open` placed first on PATH, the file is deleted and the mark goes, B restarts and the mark of a kept file is still there.

Interpretations to confirm:
(1) The list is the channel's loaded transcript, which is what `/save` resolves against (`known_attachments`) and so shares its window, `MAX_SCROLLBACK` = 500 lines per channel: a file shared further back than that is not listed, and neither can `/save <prefix>` reach it. The description calls this index the one the app already has. An uncapped per-channel file index would lift the limit for both, but means reworking `known_attachments`, `carries_file`, `channel_of_file` and `providers_for`; left alone, a follow-up if wanted.
(2) One row per share, not per file: a file sent twice is two rows, each with its own sender and date, and both show as saved once either copy is.
(3) The saved marker is per channel (channel stored name + content hash -> path), because every channel has a folder of its own: a file saved from #general is not saved in #random's folder, so #random's overlay still offers to save it there. A file saved before this change has no record, so it shows unsaved until saved again.
(4) Enter on a file that is already saved does nothing -- the bottom border offers Ctrl+O for it instead -- so a file is never saved twice by accident (`name (1).ext`). A second copy is still one `/save <prefix>` away.
(5) Enter and Ctrl+O close the overlay when they act, so the `saving...`, `saved...`, failure and `opening...` notices land in the transcript instead of behind the modal. A key that cannot act (Enter on a saved file, Ctrl+O on an unsaved one) leaves it open, as the switcher's Enter does with nothing matching.
(6) The open key is Ctrl+O ("a second key" in the criteria). In the message box an unbound Ctrl chord still types its letter, as before.
(7) Ctrl+O hands any saved file to the OS, whatever its type, so a file from a stranger with an executable type (.exe, .jar, .terminal, ...) runs as if it had been double-clicked -- and a file leyline writes carries no quarantine flag, unlike a browser download. A guard (an extension deny-list, or a confirmation) is not in the criteria and was not added; worth deciding.
(8) `NetEvent::FileSaved` now names the channel and the hash, and main.rs records every finished save in a new postcard file `saved_files` in the data directory (rewritten whole per save like the other registries). Nothing is ever pruned for being absent, so an unmounted drive doesn't erase what is known about it. Pairing and /leave leave it alone.
(9) The empty-list message is `no files have been shared in this channel yet`, which for a channel whose files are all older than (1)'s window is not quite true, as with bare `/save`'s `no file from another peer to save in this channel`.
(10) Version bumped 0.4.0 -> 0.5.0 (a feature: minor).

Measured for interpretation (7), on macOS: a file leyline saves is mode 0600 (no execute bit, so `open` cannot run a script or binary directly) and carries only `com.apple.provenance`, not `com.apple.quarantine`, so the usual downloaded-from-the-internet prompt has no flag to act on. Types with a registered interpreter or installer (.jar under an installed Java, .pkg, .dmg, .html in a browser) still launch. The decision on a guard is still open.

Follow-up after review (guard on Ctrl+O, resolving interpretation (7)): a file whose extension means it runs, installs or applies something when opened -- programs and installers, scripts, shortcuts and launchers (`files::RUNS_WHEN_OPENED`, 49 extensions: .exe .msi .jar .pkg .dmg .bat .cmd .ps1 .vbs .js .py .sh .command .lnk .url .desktop .terminal .reg .mobileconfig and the like) -- is saved like any other (Enter still saves it) but is never handed to the OS from the overlay. `files::runs_when_opened(path)` is a pure check on the saved copy's own name, which is what the OS goes by, read as written and as Windows reads it (trailing dots and blanks dropped; a `:` and what follows dropped), so `setup.exe.` and `setup.exe::$DATA` are caught like `setup.exe`; only the last extension counts (`report.pdf.exe` is refused, `setup.exe.txt` is not). `AppState::file_offer` works out once what Enter and Ctrl+O can do for a row (`FileOffer::{Save, Open(path), SavedOnly}`) and the bottom border and both keys go by it: a saved program row offers neither key, and either key says `already saved · won't open programs or scripts from here` (`FilesNotice::SavedNotOpened`). Changed: src/files.rs, src/app.rs, src/ui.rs, README (the /files row), features.md, concept.md. No version change: same task, still 0.5.0.

Not covered (a list is not a sandbox): documents that can carry macros, archives, web pages, and any type not on the list. The list is wider than one system needs (a script that merely opens in an editor on macOS is refused too), because a peer's file name says nothing about where it will be opened. Saving such a file is unaffected, and opening one by hand from the file manager is left to the user.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Added a `/files` overlay: a keyboard-first modal over a channel's shared files, newest first, with name, size, sender, date and a saved marker that survives restarts (`saved_files.rs`). Typing filters by name or sender; `Enter` saves like `/save`; `Ctrl+O` opens a saved copy with the OS default application unless its extension says it runs something (a deny-list on programs, scripts, installers and shortcuts); a key that cannot act says why in the bottom border. It works in group channels, `/msg` DMs and `/dm` chats. Verified with the unit tests (836 when built, 858 after the review follow-ups, 887 now), clippy, a scripted run of the real binary -- two instances under PTYs, 105 of 105 checks, repeated on the 0.6.0 build -- and a manual check in Warp that `Ctrl+O` opens the file.
