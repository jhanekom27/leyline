## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Every channel saves into one flat `~/Downloads/leyline/`, so files from different channels and people mix together and collide into `name (1).ext`. A stable folder per channel under a single files root is also the groundwork that the `/files` overlay, auto-save, the outbox, and synced folders all need.

Decision: the files root stays in Downloads (`~/Downloads/leyline`, as today). Only the per-channel subfolder is new.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 `/save` writes into `<files root>/<channel folder>/`, creating it on demand; filename sanitization and the `name (1).ext` collision handling are unchanged
- [x] #2 A channel folder name comes from the channel stored name, not its display label, so `/rename` and `/alias` never move it
- [x] #3 Channel folder names are safe on every platform, and two different channels never share a folder
- [x] #4 The files root defaults to `~/Downloads/leyline` as today, is a persisted setting, and a command shows where it is
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Findings (no code needed). `/save` already creates its destination folder on demand (`files::resolve_destination` runs `create_dir_all`) and main.rs hands it a flat `downloads_dir(data_dir)` on every save, so a per-channel folder is just a different `dir` passed to the same function: filename sanitization and the `name (1).ext` handling stay untouched (AC 1). A channel's stored name (`Channel::name`) is its identity (registry key, log file, `channel_kind` lookup); `/rename` only changes `AppState::renames` and `/alias` only `petnames`, and only `channel_label` reads them, so a folder derived from `Channel::name` alone can never move (AC 2). Stored names are not safe path material: `/join` takes any text, a ticket carries a name chosen by whoever shared it, and a `/msg` DM is `dm-<alias>` with whatever was typed after `/alias`.
2. Folder naming (files.rs `channel_folder` / `channel_dir`), a pure function of the stored name with no state to go stale. A name that is already a safe folder name everywhere -- lowercase ASCII letters, digits, `-` and `_`, starting with a letter or digit, at most 48 characters, not a Windows device name (`con`, `prn`, `aux`, `nul`, `com0-9`, `lpt0-9`) -- is the folder itself (`general`, `project-x`, `dm-07070707`, `p2p-08080808`). Anything else becomes `<readable part>~<first 16 hex digits of the blake3 hash of the exact stored name>`; the readable part keeps letters and digits (any script) and `_`, turns every other run of characters into one `-`, and is cut to 48 characters (`channel` if nothing is left). AC 3 holds by construction: `~` cannot occur in a plain name, so a hashed folder is never a plain one; two different names hash differently, which also separates names that differ only by case, Unicode form, punctuation or anything past the cut, so no two channels share a folder even on case-insensitive filesystems (plain names are lowercase, the hash is lowercase hex). Everything unsafe is gone before it reaches the filesystem: separators, `.` and `..`, the characters Windows refuses, control and bidi characters, trailing dots or spaces, device names, and anything over 255 bytes (at most 48 characters + 17). A golden test pins one hashed name, because changing the function later would strand existing folders.
3. Where the channel comes from (app.rs). `InputAction::SaveFile` carries `dir: PathBuf`, the folder to save into, filled by `run_save` from `files::channel_dir(files_root, stored name)`. Which channel: the active one if it carries the file, else the first joined channel that does (`AppState::channel_of_file`, built on `Channel::carries_file`), so a bare `/save` is always the active channel and `/save <prefix>` of a file shared in several lands where you are looking when it can. `AppState` holds `files_root`, seeded at startup like `browse_dir` (`load_files_root`), which keeps the path pure and unit-testable: app.rs does no I/O.
4. Files root and its command (AC 4). Persisted like the picker's remembered folder: a one-line `files_root` file in the data directory, deliberately not a field of the postcard `settings` file (a longer struct would fail to decode an existing file and silently reset the saved nickname and bell setting -- see picker.rs). `files::files_root(data_dir)` returns it, else the default `downloads_dir(data_dir)`, i.e. today's `~/Downloads/leyline`. Missing file = default; an unreadable one fails startup like `Settings::load`; one that does not hold an absolute path is logged and ignored. A bare `/folder` says where received files go: the root and the active channel's folder. `/folder <path>` also changes the root, because a persisted setting nothing can change is not one: `files::set_files_root` expands `~` and relative paths, creates the folder (a bad path fails now, not at the next save) and persists it; main applies it with `app.load_files_root`. Files saved earlier stay where they are, `/leave` never touches a channel folder, and pairing does not wipe the root (a device preference, like `browse_dir`).
5. Error clarity. `resolve_destination` explains a `dir` that is a plain file; with a nested layout the blocker is usually an ancestor (a `leyline` file in Downloads makes `leyline/general` fail with a raw `Not a directory`, the very case that message was written for). One `create_folder` helper, shared by `resolve_destination` and `set_files_root`, looks along `dir.ancestors()` for the file and names it.
6. Tests. files.rs: plain names unchanged; hashed form pinned; every awkward name (separators, `..`, `.`, Windows-illegal characters, device names in any case, trailing dots and spaces, control and bidi characters, very long, emoji-only) is one normal path component that is safe on Windows and under 255 bytes; a set of names that must all stay distinct when compared case-insensitively (case-only, sanitizes-alike, NFC vs NFD, same long prefix, a plain name vs a name shaped like a hashed folder); `channel_dir`; the root's default, persistence, relative-path rejection, `set_files_root` creating and persisting and refusing a path under a file; `resolve_destination` under a blocked ancestor. app.rs: `/save` (bare and by prefix) targets the stored-name folder (AC 1) and is not moved by `/rename` or `/alias` (AC 2); a DM and a `/dm` chat use their stored names; a file shared in two channels goes to the active one's folder, else the first's; `/folder` shows and sets (quotes stripped); the existing `/save` tests adapt. ui.rs: the hints panel still fits.
7. Docs and housekeeping: README (the `/save` rows, a `/folder` row), features.md (new entry; the earlier line saying a saved file always lands in the OS Downloads folder is updated), concept.md (File sharing section, the `files.rs` line in the project layout), `/help` and the command hints panel, and the comments that still describe a flat Downloads folder (`files.rs` module doc, `Session::data_dir`, `net::Net::save_file`). Cargo.toml 0.3.0 -> 0.4.0 (an enhancement: minor); Cargo.lock follows the build.
8. Verify with cargo test, cargo clippy --all-targets and cargo fmt --check, then the real binary: two instances under isolated HOMEs, each in a PTY read with pyte (scratch script outside the repo). A shares files in `general`, a second channel and one with an awkward name; B `/save`s each and they land in three different folders under the root; `/rename` then `/save` lands in the same folder; `/folder` shows it; `/folder <path>` survives a restart.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Built as planned, with three small differences: the files root is read in `main()` before the terminal starts (so an unreadable `files_root` file fails like the other loaders do, not mid-TUI) and reaches `AppState` through `Session`; `downloads_dir` is now private, since only `files_root` needs it; and net.rs needed no change, because `Net::save_file` never described a flat Downloads folder.

Changed: src/files.rs (new `channel_dir` / `channel_folder`, `files_root`, `set_files_root`, `create_folder`; `resolve_destination` uses `create_folder`), src/app.rs (`AppState::files_root` + `load_files_root`, `InputAction::SaveFile::dir`, new `InputAction::SetFilesRoot`, `channel_of_file`, `run_folder`, `/help`), src/main.rs (root seeded at startup, `SaveFile` uses `dir`, `SetFilesRoot` handler), src/ui.rs (`/folder [path]` hint), README (the two `/save` rows, two `/folder` rows), features.md (new entry, and the old "always lands in the OS Downloads folder" line), concept.md (File sharing section, project layout), Cargo.toml 0.3.0 -> 0.4.0 (Cargo.lock follows).

One fix the nesting made necessary: `resolve_destination` explained a `dir` that is a plain file but only looked at `dir` itself, although its comment already said "or one of its ancestors". With a folder per channel the blocker is usually the parent (a `leyline` file in Downloads makes `leyline/general` fail with a raw "Not a directory"), so `create_folder` now looks along `dir.ancestors()` and names the file in the way. Its wording changed from "create its downloads folder there" to "save files there", since the blocker can now be a parent or a custom root.

Validation: cargo test 762 passed (26 new: 16 in files.rs, 10 in app.rs; was 736), cargo clippy --all-targets clean, and cargo fmt --check flags only the old hunk in src/dm_registry.rs that this task does not touch (left alone; files.rs and app.rs were formatted on their own). The hashes pinned in the naming test come from an independent implementation (Python blake3). The real binary, two instances under isolated HOMEs each in a PTY read with pyte (scratch script outside the repo, /tmp/ley-25-6/run.py): 46 of 46 checks pass. A shared one file in #general, in "Team Alpha" and in "../../escape" (a traversal as a name, which B joined from a ticket A made); B's /save put them in <root>/general/, <root>/Team-Alpha~83f57e5b1e8db868/ and <root>/escape~ac82ee8868ab3a98/, with <root> = <HOME>/Downloads/leyline, which did not exist before, matching an independent statement of the naming rule in the script; B's HOME held nothing else besides leyline's own data. After B's /rename proj, a later /save of a file shared in that channel went to general/ again and no proj/ folder appeared. A bare /folder named the channel's folder and the root; /folder <path> created the folder and wrote it to the one-line files_root file, and the next save went there and not to the old root; after B quit and restarted, /folder still said the new root, and /save <prefix> of an already saved file went into its channel's folder there. /folder with a path under a file was refused, naming that file, and left the root alone; with a plain file where the root should be, /save said "<path> already exists and isn't a folder" instead of "Not a directory".

Not covered by that run: /alias (the unit test aliasing_a_peer_does_not_move_the_folder_of_a_conversation_with_them covers it; a DM needs /msg, which writes the real clipboard), name collisions inside a folder (unit tests: `name (1).ext` inside one channel's folder, none across channels), and Windows (AC 3 rests on a folder name only ever holding letters, digits, `-`, `_` and `~`, checked against device names, trailing dots and the 255-byte limit, not on running there).

Interpretations to confirm: (1) `/folder <path>` also changes the root. AC 4 asks for a persisted setting and a command that shows where it is; a setting nothing can change is not much of one, so the same command sets it. Easy to cut back to show-only; the command name is open too. (2) The naming scheme: a stored name that is already safe (lowercase ASCII letters, digits, `-`, `_`, at most 48 characters, not a Windows device name) is the folder; any other becomes `<readable part>~<16 hex digits of the blake3 hash of the exact name>`. It is frozen once folders exist, and LEY-25.7 and LEY-26.x build on it, so worth a look. (3) The root is kept in a one-line `files_root` file in the data directory, like the picker's `browse_dir`, not in the postcard `settings` file (a longer struct would silently reset the nickname and bell setting); pairing does not wipe it, as it is a preference of this device. (4) A file shared in several channels is saved to the active channel's folder if that carries it, else to the first joined channel that does. (5) Folders are keyed by stored name like everything else in the app: leaving a channel never touches its folder, and a different room joined later under the same name reuses it; a DM's folder is named from its stored name (dm-<alias as it was when the DM was made>), so it does not follow /alias, as AC 2 asks. (6) Files saved before this change stay in the flat root; nothing is migrated. (7) A bare /folder also names the active channel's folder, not only the root. (8) Version bumped 0.3.0 -> 0.4.0 (an enhancement: minor).

Interpretations (1) to (8) above were reviewed and accepted by Jurgen on 2026-10-13.
